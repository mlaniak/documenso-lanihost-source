# SMS User Interface Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make SMS configurable and visible without touching the database: a mobile number on each recipient, a send-time toggle, a team settings section, and delivery state on the document view.

**Architecture:** No new backend concepts. Everything here surfaces what phases 1 to 3 already built — `Recipient.phone`, `TeamGlobalSettings.smsSettings`, `DocumentMeta.smsEnabled`, and the `channel`/`kind` columns on the delivery ledger.

**Tech Stack:** React Router v7, React Hook Form, Zod, tRPC, Lingui, Tailwind, Vitest.

## Global Constraints

- Prerequisite: phases 1 to 3 merged (PR #27).
- Branch off `lanihost/main` after #27 lands, or continue `agent/sms-notifications` if it has not.
- **Run the real build after every task:** `npm run build --workspace @documenso/remix` with placeholder `NEXT_PRIVATE_DATABASE_URL`, `NEXT_PRIVATE_DIRECT_DATABASE_URL`, and `NEXT_PUBLIC_WEBAPP_URL`. Vitest does not typecheck, and this plan is almost entirely typed React and Zod. **Read `BUILD_EXIT` from the log directly — do not read the exit code of a pipeline that ends in `grep` or `tail`.**
- The build runs `lingui extract` and rewrites `packages/lib/translations/*.po`. Run `git checkout -- packages/lib/translations` before staging.
- All user-visible strings go through Lingui (`msg` / `<Trans>`), matching the surrounding components. This is UI code, so unlike the SMS message builders there is no macro-under-vitest problem here.
- **No phone number may be rendered where an email is expected**, and no signing link may appear in any UI that a non-owner can read.
- Commits are Conventional Commits. Commit after every task.

## Known shape of the work

The signer form schema is `ZAddSignersFormSchema` in `packages/ui/primitives/document-flow/add-signers.types.ts`, currently `formId`, `nativeId`, `email`, `name`, `role`, `signingOrder`, `actionAuth`. The form component is `packages/ui/primitives/document-flow/add-signers.tsx` and is **971 lines** — the densest file this plan touches, and the reason Task 2 is scoped to it alone.

Persistence runs through `packages/lib/server-only/recipient/set-document-recipients.ts` and `create-envelope-recipients.ts`. Both must carry `phone` or the field will round-trip as undefined and silently vanish, which is the most likely failure mode in this plan.

### Task 3: Team settings section

**Files:**
- Modify: `apps/remix/app/components/forms/document-preferences-form.tsx`
- Modify: the team settings tRPC mutation that accepts `TeamGlobalSettings` updates

- [ ] **Step 1: Add the fields**

Enabled, sender number, default-on, brand label, **account SID, and auth token**, validated with `ZSmsSettingsSchema` from `packages/lib/types/sms-settings.ts` so the UI and the server agree on E.164 and the 24-character brand cap.

Each business has its own Twilio account, so credentials are entered here rather than in the deployment environment.

- [ ] **Step 2: Make the auth token write-only**

Read the settings through `toPublicSmsSettings`, which omits `authToken` and exposes `hasAuthToken`. Render an empty field showing "configured" or "not set"; submitting blank means leave unchanged, and submitting a value replaces it. Encrypt with `encryptSmsAuthToken` from `packages/lib/server-only/sms/sms-credentials.ts` before storing.

**The token must never be sent to the browser**, matching how the email transport config handles SMTP passwords.

- [ ] **Step 3: Show the team's webhook URL**

Display `https://<app>/api/twilio/inbound-webhook/<teamId>` as copyable text, because it differs per team and has to be pasted into that business's own Twilio console.

- [ ] **Step 4: Validate the number against the account at save time**

Call Twilio's `IncomingPhoneNumbers` endpoint with the entered SID and token and confirm the sender number is actually owned by that account. Entering EverTrade's number under GulfVestor's credentials is an easy mistake with three accounts, and without this check it surfaces as a per-message failure long after configuration rather than as an error on the form.

Treat a network failure as "could not verify" and allow the save with a warning; treat an authoritative "not found" as a validation error.

- [ ] **Step 5: Make the failure mode legible**

When a team has no credentials, the section must say SMS is unavailable rather than accepting settings that can never send. Surface it as a disabled state with an explanation, not a silent no-op. A SID without a token counts as unconfigured.

- [ ] **Step 6: Verify the build, then commit**

```bash
git checkout -- packages/lib/translations
git commit -m "feat(sms): add an sms section to team document preferences"
```

## Verification

- `npm run test -w @documenso/lib` passes.
- `npm run build --workspace @documenso/remix` exits 0 with no type errors.
- A phone entered in the signer form survives a save-and-reload round trip. This is the specific regression to check by hand: an untouched schema anywhere in the chain drops it silently.
- The toggle persists to `DocumentMeta.smsEnabled` and the backend honours it.
- Team settings written through the UI parse with `ZSmsSettingsSchema`.

## Not included

Phone lookup from the EverTrade CRM. That was explicitly deferred in the original spec, and the seam for it is the `phone` field this plan surfaces.
